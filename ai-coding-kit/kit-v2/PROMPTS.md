# PROMPTS — 복붙해서 쓰는 프롬프트 11개 (v2)

`<>` 는 채우는 자리다. 나머지는 그대로 붙여넣는다.

**v1에서 바뀐 것.** 게이트 명령이 `node scripts/gate.mjs` 다. 검사가 번호가 아니라 이름을 갖는다
(`tests`, `regression`, `blockers`, `bypass`, `test_tamper`, `unassigned_rid`, `worktree`, `manual_checks`).
회귀 항목 마커가 `[S]`/`[A]` 에서 `[자동]`/`[수동]` 으로 바뀌었다 — v1의 글자는 S가 자동이고 A가 수동이어서
v1을 v2로 옮기던 중 실제로 뒤집어 적는 일이 일어났다. 그리고 1번·4번에 v1 미션에서 **관측된** 회피 행동에 대한 방어가 들어갔다.

| # | 이름 | 언제 | 새 세션 필요 |
|---|---|---|---|
| **1** | 작업 실행 지시 | 매 턴. 가장 많이 쓴다 | 아니오 |
| **2** | 증거 없는 완료 보고 반격 | 실행 출력 없이 "완료"가 왔을 때 | 아니오 |
| **3** | 문제·미완료 보고 추궁 | 완충 표현("임시로", "영향 없음")이 왔을 때 | 아니오 |

| 6 | 뮤테이션 지목 | `mutation:` 을 채울 때 | 아니오 |

## 1. 작업 실행 지시

매 턴 쓴다. 작업을 1개로 못 박고, 증거 형식과 정지 지점을 함께 지정한다.

```
PROGRESS.md 의 "다음에 할 작업"에 적힌 작업 1개만 수행한다. 다른 작업은 하지 마라.

순서:
1. SPEC.md 에서 이 작업이 담당하는 R-ID 와 검증 기준 칸을 인용해라.
2. 구현한다. 이번 작업 범위를 넘는 파일은 건드리지 마라.
3. 게이트를 실행한다: node scripts/gate.mjs
4. FAIL 이면 '->' 로 표시된 항목만 고치고 3번으로 돌아간다. 3회 실패하면 더 시도하지 말고 멈추고 보고한다.
5. PARTIAL(exit 3)이면 어느 검사가 SKIP 인지 그대로 적어라. PARTIAL 을 통과로 쓰지 마라.
6. 작업 중 문제를 발견하면 고치지 말고 ISSUES.md 에 한 줄 적고 멈춘다.

보고는 다음 7칸만 채운다. 산문 설명은 3줄을 넘기지 마라.
(1) 담당 R-ID
(2) 변경한 파일 목록
(3) 실행한 명령 1줄
(4) 그 명령의 출력 원문 (요약·생략 금지. 길면 runs/<날짜T시분>/ 에 저장하고 경로)
(5) 게이트의 마지막 줄과 exit code
(6) git diff --name-only HEAD 출력
(7) 다음에 할 작업 1개

게이트 보고 규칙:
- (5)에는 마지막 줄과 exit code만 적는다. 개별 검사의 PASS 를 인용해 전체가 통과한 것처럼 쓰지 마라.
- 게이트 결과가 나오기 전에 커밋 단계를 절차에 적지 마라. 결과를 보고 나서 적는다.

증거 규칙:
- 줄 수(git diff --stat)를 근거로 쓰지 마라. 환경에 따라 값이 달라진다. 파일 목록만 근거다.
- 증거 도구의 값이 네 편집 규모와 어긋나면 도구를 먼저 의심해라. 두 줄을 고쳤는데 도구가
  오백 줄이라고 하면 그 값을 붙이지 말고 어긋난다는 사실을 보고해라.

마지막에 커밋 명령을 제안하고 멈춘다. 커밋을 직접 실행하지 마라.
고치지 않은 파일을 커밋 목록에 넣지 마라.
```

**이 답이 오면 잘못된 것** — (3)(4)가 비어 있는데 "정상 동작"이라고 쓴 보고. 작업 2개를 함께 처리한 보고. 게이트 출력 없이 "통과했습니다". **개별 검사 PASS만 인용하고 전체 FAIL을 언급하지 않은 보고 — v1에서 실제로 있었다.**

## 2. 증거 없는 완료 보고 반격

실행 출력이 없는 완료 보고가 왔을 때. 논쟁하지 말고 이것만 붙인다.

```
방금 보고에 실행 증거가 없다. 그 보고는 무효로 처리한다.

다음을 순서대로 제출해라. 코드를 새로 쓰지 말고, 이미 했다고 주장한 것에 대해서만 답해라.
1. 네가 실제로 실행한 명령을 그대로 1줄씩. 실행하지 않았다면 "실행하지 않음"이라고 써라.
2. 각 명령의 출력 원문 마지막 20줄. 손으로 재구성하지 말고 실제 출력을 붙여라.
3. git diff --name-only HEAD 출력.
4. 게이트를 돌렸다면 마지막 줄과 exit code. 개별 검사의 PASS 를 인용하지 마라.
5. 위 1~4 중 지금 제출할 수 없는 항목이 있으면 "증거 없음"이라고 쓰고 왜 없는지 한 줄로 써라.

"확인했습니다", "정상적으로 동작합니다", "문제없습니다" 는 답이 아니다. 명령과 출력만 답이다.
```

**이 답이 오면 잘못된 것** — 그럴듯한 출력이 붙어 있는데 exit code·소요 시간·절대 경로·경고 줄이 하나도 없는 경우. 그건 생성된 출력이다. 같은 명령을 내 터미널에서 직접 돌려 대조한다.

## 3. 문제·미완료 보고 추궁

"일단 임시로", "영향 없습니다", "알려진 제약입니다" 가 왔을 때.

```
방금 보고에 완충 표현이 있다. 그 표현을 쓰려면 아래를 첨부해야 한다. 첨부 없이는 이 작업을 완료로 넘기지 않는다.

1. 에러·경고 원문 전체. 요약하지 마라.
2. 그 문제를 재현하는 명령 1줄과 그 출력.
3. 원인 가설 2개. 각각에 대해 "이 가설이 맞는지 확인하는 명령" 1줄.
4. 이 문제를 지금 고치지 않으면 나중에 무엇이 깨지는가. 구체적인 R-ID 로 답해라.
5. 이 문제를 ISSUES.md 형식 한 줄로 써라:
   - [ ] ISS-<번호> | blocker|major|minor | <R-ID> | 처리:<N단계> | <증거 파일:줄> | <재현 명령>

우회, 테스트 skip, 에러 무시, 하드코딩 중 하나라면 severity 는 blocker 다. 낮추지 마라.
처리: 칸은 게이트를 통과시키지 않는다. 열린 blocker 는 단계와 무관하게 게이트를 막는다.
5번을 ISSUES.md 에 적기 전까지 다음 작업을 시작하지 마라.
```

## 4. 코드베이스 완료 검증 — **별도 세션 전용**

단계가 끝났다고 판단될 때. **반드시 새 세션(빈 컨텍스트)에서 쓴다.**

> **경고 1 — 감사 사본은 "남길 목록"으로 만든다.** v1은 지울 목록이었고 그 목록으로는 감사가 무력화됐다.
> `LOG.md`(미션 기록 전체), `AGENTS.md`(살아 있으면 작업 규약이 감사 세션을 지배한다), `.git/`(커밋
> 메시지가 그대로 서술이다), 데이터 파일(경계 시험용 값이 정답을 미리 알려준다)이 v1 목록에 없었다.
>
> ```
> mkdir -p ../audit-tree
> cp SPEC.md REGRESSION.md ISSUES.md package.json .gitignore ../audit-tree/
> cp -r src ../audit-tree/          # 소스와 테스트
> cp -r scripts ../audit-tree/      # 게이트
> mkdir -p ../audit-tree/data       # 데이터 폴더는 비운 채로
> ```
>
> **경고 2 — 감사 사본에서 에이전트가 뜨는지 먼저 확인한다.** 인증·환경변수가 원본 폴더에 있었다면
> 사본에는 없다. v1에서 첫 시도가 인증 선택창에서 멈췄다.

```
너는 이 코드베이스의 감사자다. 이전에 누가 무엇을 했는지 나는 알려주지 않는다. 코드와 실행 결과만 근거로 판정해라.

SPEC.md 의 R-ID <시작>~<끝> 각각에 대해, 그 요구가 실제로 구현되어 동작하는지 판정해라.

판정 규칙:
- PASS — 해당 동작을 실행해 확인했다. 실행한 명령과 출력을 근거로 붙여라.
- PASS(수동증거) — REGRESSION.md 에 그 R-ID 의 항목이 있고, mutation: 날짜와 runs/ 증거 경로가 둘 다 있다. 셋 중 하나라도 없으면 이 판정을 쓸 수 없다.
- FAIL — 실행해 봤고 기대와 다르다. 무엇이 어떻게 달랐는지 출력으로 보여라.
- UNVERIFIABLE — 확인할 수단이 없다. 무엇이 있으면 확인 가능한지 한 줄로 써라.

각 R-ID 마다 다음 표 한 줄로 답해라. 다섯 칸이다. 칸을 줄이지 마라.
| R-ID | 판정 | 실행한 명령 | 나와야 하는 것 — 실제로 나왔는가 | 나오면 안 되는 것 — 실제로 안 나왔는가 |

마지막 두 칸에 대해:
- 검증 기준이 "A는 나오고 B는 안 나온다" 형태면 양쪽을 각각 실제 출력으로 보여라. 나온 것만 적으면 절반이 증거로 남지 않는다.
- 기준에 배제 조건이 없으면 마지막 칸에 "해당 없음"이라고 써라. 비워 두지 마라.

기준을 바꿔야 했다면 반드시 밝혀라:
- SPEC.md 의 검증 기준이 네가 실행할 수 없는 것이면(예: 외부 기기와 대조, 사람의 눈으로 판단),
  그 사실을 적고 판정을 UNVERIFIABLE 로 해라.
- 그 기준을 네가 만든 다른 기준으로 대체해서 PASS 를 내려면, 원래 기준과 대체한 기준을 나란히 적고
  왜 대체가 정당한지 한 줄로 써라. 말없이 대체하지 마라.

금지:
- 코드를 수정하지 마라. 읽고 실행만 해라.
- "구현되어 있는 것으로 보입니다" 는 판정이 아니다. 실행하거나 UNVERIFIABLE 로 판정해라.
- 함수가 존재한다는 사실을 PASS 근거로 쓰지 마라. 호출해서 결과를 봐라.

전부 PASS 라는 결론이 나오면, 그 전에 다음을 해라.
- 스텁·하드코딩된 반환값·mock 데이터·에러를 삼키는 catch 를 **구현 코드에서** 파일:줄로 찾아라.
- 테스트 파일과 골든값은 답이 아니다. 테스트의 픽스처와 기대값은 정상적으로 하드코딩되는 것이다.
  거기서 찾은 것을 제시하면 이 요구를 만족시키지 않은 것으로 본다.
- 구현 코드에 없으면 "구현 코드에서 찾지 못했다"고 그대로 써라. 억지로 3개를 채우지 마라.

마지막에 이 단계를 끝내기 위해 남은 작업을 우선순위 순으로 목록화해라. 남은 게 없으면 "없음"이라고 써라.
```

**이 답이 오면 잘못된 것**

- 전부 PASS 인데 `실행한 명령` 칸이 비어 있다. 근거가 "코드에 구현되어 있음"인 PASS.
- `나오면 안 되는 것` 칸이 비어 있거나 전부 "해당 없음"이다. 배제 조건이 있는 기준을 반쪽만 검증한 것이다.
- 스텁 지목이 전부 테스트 파일이다. **v1에서 실제로 이렇게 왔다** — `cli.test.js` 의 픽스처, `process.exit` 스텁, 기대값 문자열 셋을 제시했고 구현 코드에서는 하나도 못 찾았는데 그 사실을 말하지 않았다.
- 기준을 대체했는데 밝히지 않았다. **v1에서 "휴대폰 D-day 계산기와 대조한다"는 기준을 만나 자기 기준 5개를 만들어 넣고 PASS 를 냈다.** 대체 사실을 적지 않았다.
- 같은 세션에서 돌린 검증. 무효다.

## 5. 회귀 확인 / 재발 원인 좁히기

게이트의 `regression` 검사가 항목을 뱉었을 때, 또는 같은 버그가 두 번 이상 재발할 때.

```
게이트의 regression 검사가 다음 회귀 항목을 재확인 대상으로 지목했다.
<게이트가 출력한 항목 줄들을 그대로 붙인다>

각 항목에 대해:
1. [자동] 항목이면 그 항목을 확인하는 러너 명령을 1줄로 알려주고 실행해 출력을 붙여라.
   scripts/gate.mjs 를 쓰지 마라 — 게이트는 인자를 받지 않는 단일 진입점이다.
2. [수동] 항목이면 내가 손으로 밟을 절차를 3단계 이내로 써라. 무엇을 눌러서 무엇이 보이면 통과인지 명시해라.
3. 이번 변경이 이 항목을 깨뜨릴 수 있는 경로를 파일:줄로 지목해라. 없다고 판단하면 왜 없는지 한 줄.

확인 해시 갱신은 내가 한다. 순서는 (1) 재확인 (2) 내가 커밋 (3) 해시 갱신 (4) 내가 두 번째 커밋 이다.
너는 갱신 문안만 제안하고 REGRESSION.md 를 직접 고치지 마라.

그리고 같은 증상이 반복되고 있다면 공유 지점을 조사해라. 다음을 각각 파일:줄로 열거하고, 중복·순서 의존이 있는 곳을 표시해라.
- 이 동작이 읽고 쓰는 저장 위치(파일 경로, 전역 변수, 캐시)
- 같은 이벤트·입력에 등록된 처리기가 2개 이상인 곳과 등록 순서
- 한쪽이 다른 쪽의 효과를 덮거나 흡수하는 지점

원인 후보를 1개로 좁히고, 그것이 원인인지 확인하는 명령이나 절차를 1개 제시해라. 코드는 수정하지 마라.
```

## 6. 뮤테이션 지목 — 검증 장치가 실패를 실제로 잡는지

`mutation:` 날짜를 채울 때. **코드를 읽지 못해도 밟을 수 있게** 만드는 프롬프트다.

**v2에서 적용 범위가 넓어졌다.** v1은 회귀 항목에만 썼다. 이제 셋 다에 쓴다.

| 대상 | 무엇을 확인하는가 |
|---|---|
| 회귀 항목 | 그 항목이 동작 파손을 잡는가 |
| 테스트 케이스 | 그 단정문이 실패를 잡는가 — **v1에서 테스트가 결함을 정답으로 고정한 일이 두 번 있었다** |
| 게이트 검사 | `node scripts/gate-selftest.mjs` 가 자동으로 한다. 사람이 손으로 하지 않는다 |

```
<R-ID 또는 테스트 이름> 을 일부러 고장 내는 최소 변경을 1곳만 파일:줄로 지목해라.

조건:
- 코드를 수정하지 마라. 내가 손으로 붙여넣을 것이다.
- 지목은 정확히 1곳. 두 곳 이상 제시하지 마라.
- 되돌리기 쉬운 것을 우선해라 (한 줄 추가, 한 줄 주석 처리, 비교 연산자 한 글자).
  여러 파일을 고쳐야 하는 것은 제시하지 마라.
- 다음 3개를 함께 줘라: (1) 파일:줄 (2) 붙여넣을 코드 1줄 (3) 원복 명령 (git restore <파일> 형태)
- 그 변경을 넣었을 때 내가 화면에서 무엇을 보게 되는지, 또는 어떤 명령이 실패하는지 한 줄로 예고해라.
- 경계 조건이 있는 기준이면 경계를 노려라. 예: 포함/제외 경계에서 <= 를 < 로 바꾸는 것.
```

내가 할 일: 붙여넣고 → **실패하는 것을 눈으로 본다** → 원복 → `mutation:` 을 오늘 날짜로 갱신.
실패가 관찰되지 않으면 그 항목·테스트는 아무것도 검증하지 못하는 것이므로 문장을 다시 쓴다.

> v1 7단계에서 `next` 명령의 경계(`<= days` → `< days`)를 이 방법으로 깨뜨렸더니 테스트가 실제로
> 실패했다. 그게 그 테스트가 경계를 지키고 있다는 유일한 증거였다.

## 7. 세션 인계

세션을 끝낼 때. 다음 세션은 이 파일만 읽고 이어간다.

```
이 세션을 끝낸다. HANDOFF.md 를 아래 형식으로 작성해라. 추측을 쓰지 말고 이 세션에서 실제로 일어난 것만 써라.

# HANDOFF (<오늘 날짜>)
## 마지막 커밋
<git log --oneline -1 출력>
## 마지막 green 태그
<git tag 출력에서 실제로 존재하는 것만. 찍지 않은 태그를 적지 마라>
## 지금 미완료로 남은 것
<R-ID 와 함께. 없으면 "없음">
## 이번 세션에서 결정된 사항 (뒤집지 말 것)
<결정과 이유. SPEC.md 에 이미 반영된 것은 "SPEC 반영됨"이라고 표시>
## 시도했고 실패한 접근 (다시 시도하지 말 것)
<무엇을 왜 시도했고 어떻게 실패했는지. 이게 가장 중요하다>
## 다음 세션이 첫 번째로 할 일
<정확히 1개>
## 아직 사람에게 물어봐야 하는 것
<없으면 "없음">

작성 후 SPEC.md 와 PROGRESS.md 에 반영되지 않은 결정이 있으면 그 목록을 따로 알려라.
```

> `마지막 green 태그` 칸을 `git tag` 출력으로 못박는 이유. v1에서 모델이 **존재하지 않는
> `green/stage3` 태그**를 상태 파일에 적었다. 인계 문서에서 같은 일이 일어나면 다음 세션이
> 없는 지점으로 되돌리려 한다.

## 8. 명세 인터뷰

프로젝트 시작. 뭘 만들지 흐릴 때. **모델에게 명세를 쓰게 하는 게 아니라, 내가 쓸 수 있게 질문을 받는 것이다.**

```
나는 <만들고 싶은 것 3~10줄로 설명>을 만들려고 한다.

명세를 내가 직접 쓸 수 있게 도와줘라. 코드나 계획은 쓰지 마라. 지금은 질문만 한다.

1. 내 설명에서 네가 임의로 가정해야 하는 지점을 5개 이하로 골라, 각각 선택지와 함께 물어라. 한 번에 5개까지만.
2. 내가 답하면, 답을 아래 3열 표로 정리해라. 열 이름을 바꾸지 마라.
   | R-ID | 동작 문장 (누가 / 어떤 상황에서 / 무엇을 하면 / 무엇이 보인다) | 검증 기준 |
   R-ID 는 R-001 부터 3자리로 붙여라.
3. 검증 기준은 **기계가 잴 수 있는 문장**으로 써라. 이게 이 프롬프트의 핵심이다.
   되는 예: "모든 행이 정확히 28칸이다", "dday 2026-09-15 2026-12-25 가 101 을 출력한다",
            "오늘+7 이 나오고 오늘+8 은 나오지 않는다"
   안 되는 예: "휴대폰 계산기와 대조한다", "정렬이 맞아 보인다", "자연스럽다", "테스트가 통과하면 된다"
4. 기계로 잴 수 없는 요구는 버리지 말고 별도 목록으로 모아라. 그건 CHECKS.md(사람이 눈으로 판정하는 표)로 간다.
   그 목록의 각 항목에 "내가 무엇을 하면 무엇이 보이면 통과인가"를 붙여라.
5. 3열을 채울 수 없는 요구가 있으면 그 행을 "판별 불가"로 표시하고, 무엇이 정해지면 채울 수 있는지 써라. 억지로 채우지 마라.
6. 마지막에 "만들지 않는 것" 후보를 5개 제안해라. 내가 고르면 비목표가 된다.

우선순위는 표에 넣지 말고 표 아래 목록으로 따로 써라.
```

**이 답이 오면 잘못된 것** — 검증 기준이 "테스트가 통과하면 된다" 처럼 순환하는 문장. 그건 기준이 아니다.
**그리고 외부 기기·사람의 눈에 의존하는 기준.** 자동 감사에서 그 항목은 조용히 다른 기준으로 대체된다 — v1에서 실제로 일어났다.

## 9. 구현 옵션 3안 비교

구조·언어·라이브러리·저장 방식을 정할 때. 하나를 추천받는 게 아니라 **비교표를 받아 내가 고른다.**

```
<정해야 하는 것>을 구현하는 방법을 3가지 제시해라. 아직 코드를 쓰지 마라.

각 안에 대해 다음 표 한 줄로 답해라.
| 안 | 어떻게 동작하는가 (2문장) | 데이터가 어디에 어떤 형태로 남는가 | 이 안을 고르면 포기하는 것 | 나중에 바꾸기 어려워지는 것 | 내가 눌러서 확인할 수 있는가 |

그리고 표 아래에:
- 세 안이 갈리는 진짜 쟁점 1개를 한 문장으로.
- 각 안이 SPEC.md 의 검증 기준을 만족시키지 못하는 지점이 있으면 R-ID 로 지목해라. 없으면 "없음".
- 내가 아직 말하지 않았지만 이 선택에 영향을 주는 조건 3개를 질문으로.
- 네가 추천하는 안과 그 이유 2줄. 단, 내가 다른 것을 고를 수 있게 추천은 마지막에만 써라.
```

**고른 뒤 할 일** — 반려한 두 안의 이유를 `SPEC.md` 의 비목표·불변 규칙으로 옮긴다. 옮기지 않으면 모델이 나중에 그 안으로 되돌아간다.

> v1 6단계에서 이 프롬프트가 가장 잘 작동했다. 모델이 방안 B의 한계를 **스스로 밝혔고**
> ("두 자리 일정의 경우 여전히 결합"), 그 고백이 방안 A를 고른 근거가 됐다.
> **고치기 전에 방식을 제안하고 멈추게 하는 것이 실제로 효과가 있었다.**

## 10. 계층 계획 수립

명세를 동결한 직후 1회.

```
SPEC.md 를 읽고 전체 구현 계획을 PLAN_L1.md 로 작성해라. 코드는 쓰지 마라.

규칙:
1. 1단계는 기능 우선순위가 아니라 "내가 손으로 끝까지 밟을 수 있는 가장 얇은 관통 경로" 하나로 정해라.
   데이터가 실제 저장 위치에 기록되고 다시 읽히는 것까지 포함해야 한다.
2. 각 단계는 [ ] 체크박스 한 줄로 쓰고, 담당 R-ID 를 전부 열거하고, "종료조건: 내가 무엇을 해서 무엇을 보면 이 단계가 끝인가"를 붙여라.
3. 단계는 8개 이하로 만들어라. 넘으면 묶어라.
4. 마지막에 커버리지 표를 붙여라: SPEC.md 의 R-ID 전부 × 배정된 단계. 배정 안 된 R-ID 가 있으면 그 개수를 명시해라. 0 이 아니면 계획이 미완이다.
5. 아직 정해지지 않아 계획을 세울 수 없는 부분은 단계로 만들지 말고 "선결 질문"으로 따로 모아라.

각 단계 안의 세부 작업은 지금 쪼개지 말아라. 그 단계를 시작할 때 따로 요청한다.
```

> 단계 수의 실측. v1은 요구 7개 → 단계 7개였다. **대략 요구 하나에 단계 하나**다. 규칙 4번 때문에
> 요구 수가 단계 수의 하한을 정한다. 요구를 먼저 세고 단계를 정한다 — 반대로 하지 않는다.

## 11. 인수 프로젝트 인벤토리

남의 코드를 받았을 때 **가장 먼저**. 명세가 없는 상태에서 출발점을 만든다.

```
이 코드베이스를 인수했다. 나는 이 코드를 읽지 못한다. 코드를 수정하지 마라. 읽고 실행만 해라.

1. 이 프로젝트를 실행하는 명령과, 실행됐는지 확인하는 방법을 알려줘라. 실행이 안 되면 무엇이 없어서 안 되는지 알려라.
2. 사용자가 손으로 확인할 수 있는 기능을 최대 15개 열거해라. 각각 다음 형식으로.
   | 기능 | 내가 무엇을 하면 무엇이 보이는가 | 관련 파일:줄 | 자동 확인 가능? |
3. 내가 추가하려는 것은 <추가할 기능> 이다. 이것과 충돌하거나 겹칠 수 있는 기존 경로를 파일:줄로 지목해라. 특히 같은 입력·이벤트를 이미 처리하는 곳.
4. 이 프로젝트에 테스트가 있는가. 있으면 실행 명령과 현재 통과 여부를, 없으면 "없음"이라고 써라.
5. 손으로 눌러서만 확인 가능한 기능이 몇 개인지 세어라.
6. 에러를 삼키는 곳(본문이 비었거나 주석뿐인 catch)을 파일:줄로 열거해라. 고치지는 마라.

계획을 세우지 마라. 지금은 현황만 만든다.
```

**받은 뒤 할 일 — 이게 인수 프로젝트의 순서다**

1. 2번 목록에서 **내가 직접 눌러 되는 것만** `SPEC.md` 표에 R-ID로 등록한다. 모델의 주장만으로 등록하지 않는다.
2. 등록한 것 전부를 `REGRESSION.md` 항목으로 만든다. `의존:` 에 3번에서 받은 파일 경로를 넣는다. **이 단계를 건너뛰면 회귀를 잡을 수 없다.**
3. 자동 확인이 불가능한 항목은 `[수동]` 으로 넣고, `CHECKS.md` 에 그 항목 줄을 만든다.
4. 6번 목록은 `ISSUES.md` 에 `major` 로 등재한다. 게이트의 `bypass` 검사가 인수 첫날부터 울릴 것이다 — **그건 고장이 아니라 인수한 코드의 상태다.** 하나씩 줄여 나간다.
5. 그 다음 추가할 기능을 새 R-ID로 등록하고 프롬프트 1로 넘어간다.
