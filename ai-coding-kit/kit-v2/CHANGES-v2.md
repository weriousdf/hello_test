# v1 → v2 — 무엇이 왜 바뀌었는가

v1 을 `dday-cal` 미션으로 한 사이클 완주하고 나온 관측을 반영했다.
미션 기록은 `D:\gwanmun-lab\dday-cal\LOG.md` 에 있다. 아래 모든 항목의 근거가 그 파일이다.

**관측 조건.** 요구 7개, 단계 7개, 파일 하나, 텍스트 입출력. 작업 모델은 `gemini-3.5-flash` 였다
(핀은 3.8-flash 였으나 CLI 가 그 이름을 몰라 표시만 했다 — 세션 로그 521턴 전부 3.5-flash).
**사람이 전부 지켜볼 수 있는 크기에서 얻은 결론이다.** 큰 코드베이스에서도 같은지는 아직 모른다.

## 구조가 바뀐 것 셋

**게이트가 PowerShell 에서 node 로 옮겼다.** `gate.ps1` → `scripts/gate.mjs`.
v1 미션에서 PowerShell 때문에 잃은 시간이 실제로 있었다 — `&&` 파서 오류, BOM 유무로 인한 한글 깨짐,
`$T` 와 `$t` 가 같은 변수인 것. 그리고 node 는 이미 프로젝트 의존성이었다.
이제 Windows·Linux·컨테이너에서 같은 파일이 돈다. Codex 클라우드 같은 Linux 환경에서도 그대로 쓴다.

**게이트를 검사하는 파일이 생겼다.** `scripts/gate-selftest.mjs`.
v1 에서 8개 검사 중 2개가 죽은 채 통과를 내고 있었다. 게이트가 스스로 신고하지 않았고 사람이
우연히 스크립트를 읽어보고서야 발견했다. selftest 는 검사마다 위반 픽스처를 만들어
**민감도**(위반을 만들면 FAIL 이 나오는가)와 **특이도**(정상 상태에서 조용한가)를 판정한다.
`gate.mjs` 가 바뀔 때만 돈다 — 단계당 비용은 0 이다.

**검사에 등급이 붙었다.** `확정` 과 `유예`.
확정 = selftest 를 통과하고, **v1 미션에서 실제로 울려 무언가를 막은 것이 관측됐다** (`tests`, `regression`, `blockers`).
유예 = selftest 는 통과하지만 실전에서 울린 기록이 없다 (나머지 5개).
유예 검사가 다음 사이클에서도 울리지 않으면 뺄 후보다. **울리지 않는 검사는 통과에 근거를 보태지 않으면서 매 단계 비용만 먹는다.**

## v2 를 만들면서 새로 나온 것 여섯

**16. 검사 2 가 조용한 catch 를 놓쳤다.**
v1 에서 모델이 `catch (e) { // Ignore or handle }` 을 남겼다. `AGENTS.md` 는 에러 무시를 blocker 급으로
규정하는데 검사 2 는 못 봤다. **한 번도 울리지 않은 검사의 침묵은 안전 신호가 아니다.**
v2 는 표식 문자열에 더해 **본문이 비었거나 주석뿐인 catch** 를 잡는다.

**17. selftest 픽스처를 쓸 때 지킬 규칙 두 개가 생겼다.** 둘 다 실패한 자리에서 나왔다.

*규칙 1 — 픽스처는 실제 작업 상태를 재현한다. 최소 상태를 만들지 않는다.*
v1 RUNBOOK §1.4 에 **이미 수동 selftest 의례가 있었다**. `SPEC.md` 에 `R-099` 를 한 줄 넣고 검사 6 이
FAIL 을 내는지 눈으로 보는 것. 그런데 그 의례는 `PROGRESS.md` 없이 시험했고, 검사 6 의 버그는
R-ID 가 `PROGRESS.md` 에 적혀 있을 때만 드러났다. **실측했다** — 버그 있는 게이트에 `R-099` 만 넣으면
FAIL(정상처럼 보임), `PROGRESS.md` 에도 적으면 PASS(버그 발현). **의례를 지켜도 버그를 못 본다.**
그래서 v2 의 기여는 selftest 아이디어가 아니다. 자동화, 8개 전부 커버, 그리고 **픽스처가 실제 상태를 재현하는 것** 이다.

*규칙 2 — 원장에는 항목을 여러 개 두고, 위반은 첫 항목이 아닌 것에 건다.*
항목이 하나면 `items[0]` 만 보고 루프를 돌지 않는 게이트도 통과한다.

**18. 게이트가 자기 파일을 스캔해서 자기 탐지 문자열을 우회 흔적으로 신고했다.**
갓 설치한 키트가 무조건 FAIL 이었다. `CONFIG.gateFiles` 로 제외했다.
**그리고 이 버그를 selftest 가 놓쳤다** — 픽스처에 `scripts/` 를 복사하지 않았기 때문이다.
실제 프로젝트에는 게이트 파일이 저장소 안에 있다. 규칙 1 을 만들자마자 내가 어겼다.

**19. `SPEC.md` 템플릿의 예시 행 `R-001` 이 게이트를 트립시켰다.**
검증 수단이 없는 R-ID 이므로 `unassigned_rid` 가 정당하게 FAIL 을 냈다. 예시를 `R-NNN` 으로 바꿨다 —
게이트는 `R-\d{3}` 만 R-ID 로 센다.

**20. `RUNBOOK.md` §1.3 에 적은 기대값이 틀렸다.**
"갓 설치하면 PARTIAL 이 정상" 이라고 썼는데 실제로는 FAIL 이다 — 명세가 비어 있으니 `unassigned_rid` 가
울린다. **명세가 없는데 통과를 내면 안 되므로 FAIL 이 옳다.** 문서를 실측값으로 고쳤다.
설치 진행에 따른 판정은 이렇게 움직인다: 갓 설치 `FAIL` → SPEC·러너 세운 뒤 `PARTIAL` → 첫 회귀 항목 등록 뒤 `PASS`.


**21. `[S]`/`[A]` 마커가 외워야 아는 표기였고, v1 을 v2 로 옮기던 중 실제로 뒤집혔다.**
v1 은 `S = 자동으로 돌릴 수 있는 항목, A = 사람이 손으로 눌러야 하는 항목` 이었다.
v2 템플릿을 쓰면서 정반대로 적었다 — 게이트는 `[SA]` 를 둘 다 같게 처리하므로 기능은 깨지지
않았지만 문서가 서로 모순이 됐다. **v1 을 읽으면서 옮기던 중에 뒤집혔다는 것이 표기법의 문제라는 증거다.**
글자를 버리고 `[자동]` / `[수동]` 으로 바꿨다. 게이트 정규식도 함께 바꿨다.

## v1 미션에서 온 것이 아닌 v2 자체의 추가

**감사 프롬프트에 "기준을 대체했으면 밝혀라" 를 넣었다.**
v1 에서 감사자가 "휴대폰 D-day 계산기와 대조한다" 는 기준을 만나 **자기 기준 5개를 만들어 넣고
PASS 를 냈고, 대체 사실을 적지 않았다.** 이제 프롬프트가 원래 기준과 대체한 기준을 나란히 적게 하고,
실행할 수 없는 기준은 UNVERIFIABLE 로 판정하게 한다.

**`mutation:` 의 적용 범위를 셋으로 넓혔다.**
v1 은 회귀 항목에만 썼다. v2 는 회귀 항목·**테스트 케이스**·게이트 검사 셋 다에 적용한다.
테스트에 적용하는 이유는 ISS-001·ISS-002 가 둘 다 **테스트가 결함을 정답으로 고정한** 경우였기
때문이다. 게이트 검사는 `gate-selftest.mjs` 가 자동으로 한다.

**세션 인계 프롬프트에 `마지막 green 태그` 칸을 `git tag` 출력으로 못박았다.**
v1 에서 모델이 존재하지 않는 `green/stage3` 태그를 상태 파일에 적었다. 인계 문서에서 같은 일이
일어나면 다음 세션이 없는 지점으로 되돌리려 한다.

**인수 프로젝트 인벤토리에 "에러를 삼키는 곳을 열거해라" 를 넣었다.**
그리고 그 목록을 `major` 로 등재하게 했다 — 인수 첫날부터 `bypass` 검사가 울리는 것은
고장이 아니라 인수한 코드의 상태다.

## 아직 안 한 것 — 정직하게

- **`WHY.md`**(해석) 를 안 옮겼다. **의도적으로 미룬다.** 이 문서는 "각 장치가 무엇을 막는가" 를
  설명하는데, `유예` 검사 5개가 실전에서 무엇을 막는지 아직 모른다. 한 사이클치 근거로 쓰면 두 번째
  사이클 뒤에 다시 써야 한다.
- **`EXAMPLES.md`**(채워진 예시) 를 안 옮겼다. `scripts/gate-selftest.mjs` 의 정상 픽스처가 이미
  작동하는 예시다 — 요구 2개, 테스트 2개, 회귀 항목 2개, 형식이 전부 맞고 게이트가 exit 0 을 낸다.
  별도 파일로 다시 쓰는 것보다 그것을 가리키는 편이 정확하다.
- **비결정 영역이 비어 있다.** 이 키트 전체가 "이걸 하면 이게 보인다" 라는 재현 가능성을 전제로 서 있다.
  에이전트의 출력 품질처럼 두 번 돌리면 다른 것에는 회귀 항목이 아니라 **eval set**(입력 여러 개 +
  채점 기준 + 통과율 임계값)이 필요하다. **그 층은 아직 없고, 실제로 돌려보기 전에는 상상해서 쓰지 않는다** —
  v1 의 15개가 나온 이유가 돌려봤기 때문이다.
- **화면이 있는 프로젝트에서 시험되지 않았다.** `manual_checks` 검사는 v1 미션에서 항목이 0개여서
  한 번도 시험되지 않았다. 기계가 못 재는 판정이 여기로 오는데, CLI 미션에는 그런 것이 없었다.

## 남은 판단 — 게이트를 3개로 줄일 것인가

사이클 직후의 정직한 판정은 "8개는 과설계고 3개만 실증됐다" 였다. 그런데 selftest 를 만들어 걸어보니
**8개 전부 통과한다.** 검사 2·3·6 이 의심스러웠던 이유는 아이디어가 틀린 게 아니라 **구현이 깨져 있었기**
때문이었다. 그래서 8개로 간다.

다만 `유예` 5개는 다음 사이클의 관측 대상이다. **selftest 통과는 "이 검사가 실패를 낼 수 있다" 는
증거일 뿐 "이 검사가 실전에서 무언가를 막는다" 는 증거가 아니다.** 두 번째 사이클에서도 울리지 않는
검사는 뺀다.

그리고 selftest 자체의 한계를 잊지 마라. **selftest 는 자기 픽스처만큼만 좋다.** v1 의 검사 2 에
`TODO` 픽스처로 selftest 를 걸었다면 통과했을 것이고, 조용한 catch 는 계속 놓쳤을 것이다.
완전히 닫힌 것은 "검사가 죽었다" 는 구멍이고, "검사가 불완전하다" 는 구멍은 **픽스처로 써넣은
위반 종류만큼만** 닫힌다. 새 위반 종류를 실전에서 만나면 그때 픽스처로 추가한다.
