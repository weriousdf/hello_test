# RUNBOOK — 이 키트를 어떻게 쓰는가 (v2)

AI 에이전트에게 코딩을 시킬 때 쓰는 운영 절차다. 판정 근거를 모델의 말에서 **관찰 가능한 산출물**로 옮기는 것이 전부다.
왜 각 장치가 있는지는 `WHY.md`를 보라. 이 파일은 순서만 다룬다.

**v1과 무엇이 다른가** 는 `CHANGES-v2.md`에 있다. 요지는 셋이다.
게이트가 PowerShell에서 **node**로 옮겨 어느 OS·어느 에이전트에서도 같은 파일이 돈다.
게이트를 검사하는 `gate-selftest.mjs`가 생겼다 — v1에서 8개 중 2개가 죽은 채 통과를 내고 있었다.
v1이 문서에만 적어두고 기계로 막지 않던 것들을 기계로 옮겼다.

| 파일 | 역할 | 누가 고치는가 |
|---|---|---|
| `RUNBOOK.md` | 이 파일. 절차 | 사람 |
| `AGENTS.md` | 에이전트가 매 세션 읽는 규약 (`CLAUDE.md`·`GEMINI.md`로 개명 가능) | 사람 |
| `SPEC.md` | 요구 목록. R-ID와 검증 기준 | **사람만** |
| `PROGRESS.md` | 진행 상태. 컨텍스트가 날아가도 남는 진실 | 모델이 갱신, 사람이 확인 |
| `REGRESSION.md` | 한 번 동작한 것의 원장 | 모델이 제안, 사람이 붙여넣기 |
| `ISSUES.md` | 미해결 문제 원장 | 모델이 적고, 사람만 닫는다 |
| `CHECKS.md` | 손으로 눌러 확인한 기록. 기계가 못 재는 것의 유일한 근거 | **사람만** |
| `PROMPTS.md` | 복붙용 프롬프트 | 사람 |
| `WHY.md` | 해석 — 각 장치가 무엇을 막는가 | 사람 |
| `scripts/gate.mjs` | 게이트. 검사 8개 | **사람만** |
| `scripts/gate-selftest.mjs` | 게이트를 검사한다. 게이트가 바뀔 때만 돈다 | **사람만** |

## 1. 설치 — 첫 40분

각 단계에 **다음으로 넘어가는 조건**이 있다. 조건이 안 맞으면 다음 단계로 가지 마라.

### 1) 파일 복사

프로젝트 루트에 키트를 복사한다. `.md`는 전부 **UTF-8**이다. 편집기에서 ANSI/CP949로 저장하면 한글이 깨지고 게이트가 항목을 세지 못한다.

```
node -v
```

**조건** node가 18 이상이다. v1의 BOM 고정 의례는 없어졌다 — 게이트가 node라 BOM에 영향받지 않는다.

### 2) 기준선 커밋과 태그

```
git init
git add -A
git commit -m "chore: 키트 기준선"
git switch -c work/setup
git tag green/day0
git tag
```

**조건** 마지막 `git tag`가 `green/day0` 한 줄을 출력한다. 커밋이 0개인 상태에서는 태그를 달 수 없다. 순서를 바꾸지 마라.

### 3) 게이트를 처음 돌려 본다

```
node scripts/gate.mjs
```

**조건** `CHECK <id> <verdict>` 줄이 8개 찍힌다.

이 시점에는 **`GATE: FAIL`(exit 1)이 정상이다.** 아래가 갓 설치한 상태의 정확한 판정이다.

```
[PASS] worktree        미추적 파일 0개
[SKIP] tests           테스트 명령이 없다          ← 아직 package.json 에 test 가 없다
[PASS] bypass          우회 흔적 0줄
[PASS] test_tamper     기존 테스트·골든 수정·삭제 0개
[PASS] blockers        열린 blocker 0건
[FAIL] unassigned_rid  SPEC.md 의 R-ID 가 0개      ← 명세를 아직 안 썼다
[SKIP] regression      회귀 항목 0건               ← 아직 확인한 동작이 없다
[PASS] manual_checks   수동 체크표 빈칸 0줄
```

**명세가 비어 있는데 게이트가 통과를 내면 안 된다.** 대조 기준이 없는 상태에서 낸 PASS는 근거가 없다. 그래서 이 FAIL은 고장이 아니라 게이트가 제 일을 하는 것이다.

판정은 설치를 진행하면서 이렇게 움직인다.

| 시점 | 결과 | 이유 |
|---|---|---|
| 갓 설치 | FAIL | `unassigned_rid` — 명세가 비었다 |
| SPEC 를 채우고 테스트 러너를 세운 뒤 | PARTIAL (exit 3) | `regression` 이 SKIP — 아직 회귀 항목이 없다 |
| 첫 회귀 항목을 등록한 뒤 | PASS (exit 0) | 여기서부터 통과가 근거를 갖는다 |

**PARTIAL도 통과가 아니다.** SKIP은 '검사하지 못했다'는 뜻이고, 못 한 검사는 통과에 근거를 보태지 않는다.

### 4) 게이트가 실패를 실제로 잡는지 확인한다 — 건너뛰지 마라

```
node scripts/gate-selftest.mjs
```

**조건** `SELFTEST: PASS`. 하나라도 `못잡음`이면 그 검사는 꺼져 있는 것이고, **고치기 전에는 게이트의 PASS를 근거로 쓸 수 없다.**

> v1에는 이 자리에 손으로 하는 의례가 있었다. `SPEC.md`에 `R-099`를 한 줄 넣고 검사가 FAIL을 내는지 눈으로 보는 것이었다. **그 의례는 실패했다.** 검사 6의 버그는 R-ID가 `PROGRESS.md`에 적혀 있을 때만 드러났는데, 의례는 `PROGRESS.md` 없이 시험했다. 실측으로 확인했다 — 버그 있는 게이트에 `R-099`만 넣으면 FAIL(정상처럼 보임), `PROGRESS.md`에도 적으면 PASS(버그 발현). **픽스처에서 무언가를 빼면 그것 때문에 생기는 버그를 볼 수 없다.** 그리고 손으로 하는 의례는 한 번 하고 잊는다. 게이트를 고친 뒤 다시 하지 않는다.

**`gate.mjs`를 고쳤으면 그때마다 selftest를 다시 돌린다.** 설치 때 한 번이 아니다.

### 5) SPEC.md를 채운다

`PROMPTS.md` 8번(명세 인터뷰)을 붙여 질문을 받고, 답을 사람이 직접 `SPEC.md` 표에 옮긴다.

**조건** `검증 기준` 칸의 빈 칸이 **0개**다. 그리고 각 기준이 **기계가 잴 수 있는 문장**이다.

> 이게 v2에서 가장 중요한 규칙이다. v1의 `R-006` 기준은 "휴대폰 D-day 계산기와 대조한다"였다. 자동 감사에서 감사자는 휴대폰이 없다. 그래서 **자기 기준을 만들어 넣고 통과를 냈고, 기준을 바꿨다는 말은 하지 않았다.** 기계가 못 재는 기준은 조용히 대체된다.
>
> 기계가 잴 수 있는 문장: `모든 행이 정확히 28칸이다`, `dday 2026-09-15 2026-12-25 이 101 을 출력한다`
> 기계가 못 재는 문장: `휴대폰과 대조한다`, `자연스럽게 보인다`, `사용하기 편하다`
>
> 기계가 못 재는 것은 **버리지 말고** `CHECKS.md`로 옮긴다. 그러면 게이트의 `manual_checks` 검사가 빈칸을 세서 사람이 채웠는지 확인한다. 화면이 있는 프로젝트에서는 이쪽이 주력이 된다.

### 6) T0 작업 하나로 전 절차를 리허설한다

문구 하나 바꾸는 수준의 잡일을 골라 `PROMPTS.md` 1번으로 지시한다. 목적은 결과물이 아니라 절차를 한 바퀴 도는 것이다.

**조건** 완료 보고를 받았고, 게이트를 돌렸고, 사람이 커밋했고, `PROGRESS.md`가 갱신됐다.

### 7) 관측 조건을 못박는다 — v2 신규

`PROGRESS.md`의 `작업 모델` 칸을 채운다. **그 값을 무엇으로 확인했는지 함께 적는다.**

> v1 미션 전체를 `gemini-3.8-flash`로 돌렸다고 기록했는데, 사실이 아니었다. 세션 로그의 서빙 모델 필드 **521턴 전부가 `gemini-3.5-flash`** 였다. 설정 파일과 `-m` 플래그와 상태 바가 전부 3.8을 가리키고 있었지만, CLI가 그 이름을 몰라서 표시만 하고 자기 기본 모델로 요청을 보냈다. **상태 바는 요청한 이름을 보여줄 뿐 서빙 모델이 아니다.**
>
> 근거로 쓸 수 있는 것: 세션 로그의 서빙 모델 필드, 종료 요약의 사용량 표, 응답 헤더의 모델 ID.
> 근거로 쓸 수 없는 것: 상태 바, 설정 파일, 내가 지정한 플래그.

**조건** `작업 모델` 칸에 모델 이름과 그 근거가 함께 적혀 있다. 이걸 안 하면 미션이 끝난 뒤 "어느 모델이 이렇게 했나"를 말할 수 없다.

### 인수 프로젝트라면 순서가 다르다

명세가 아니라 **이미 되던 동작**에서 출발한다. 위 1)~4) 다음에:

1. `PROMPTS.md` 11번(인벤토리)으로 현황 확보. 계획은 아직 세우지 않는다.
2. 받은 목록에서 **사람이 직접 눌러 되는 것만** `SPEC.md`에 R-ID로 등록한다. 모델의 주장만으로 등록하지 않는다.
3. 등록한 전부를 `REGRESSION.md` 항목으로 만들고 `의존:`에 관련 파일 경로를 넣는다. **이걸 건너뛰면 회귀를 못 잡는다.**
4. 자동 확인 불가 항목은 `[A]`로 넣고 `CHECKS.md`에 줄을 만든다.
5. 그 다음에 추가할 기능을 새 R-ID로 등록하고 6)으로 간다.

## 2. 매일 도는 루프

작업 1개 단위. 이걸 반복하는 것이 전부다.

```
   ┌─ PROGRESS.md 의 "다음 작업" 1개 확인                        (1분)
   │
   ├─ PROMPTS.md 1번 붙여넣고 지시                               (1분)
   │
   ├─ 완료 보고 수신
   │     증거가 없다 ───────────────► PROMPTS.md 2번으로 반격 ──┐
   │     완충 표현이 있다 ───────────► PROMPTS.md 3번으로 추궁 ──┤
   │                                                              │
   ├─ 게이트 결과 확인                                    ◄───────┘
   │     exit 1 (FAIL)  → '->' 항목만 고치게 지시. 3회 실패하면 정지
   │     exit 3 (PARTIAL) → 통과 아님. 어느 검사가 SKIP 인지 기록
   │     exit 0 (PASS)  → 다음으로
   │
   ├─ git diff --name-only HEAD 를 예상과 대조                   (1분)
   │     예상 밖 파일 3개 이상 → 커밋 말고 정지
   │
   ├─ 사용자에게 보이는 변경이면 사람이 직접 눌러 확인           (3~10분)
   │     + 게이트 regression 검사가 지목한 회귀 항목도 함께
   │     + CHECKS.md 에 결과와 runs/ 경로를 사람이 채운다
   │
   ├─ 사람이 커밋한다 (모델이 아니라)                            (1분)
   │
   └─ PROGRESS.md 갱신 / REGRESSION.md 항목 추가 제안을 받아 붙여넣기
```

**`git diff --stat`을 근거로 쓰지 마라. `--name-only`를 쓴다.**

> v1에서 모델이 두 줄을 고치고 `src/cli.js | 583` 을 근거로 붙였다. 그 셸의 git 설정이 시스템 설정을 억제해 `core.autocrlf`가 꺼져 있었고, CRLF 작업 파일이 LF 블롭과 전 줄 불일치로 잡혔다. **같은 트리에 게이트를 걸었더니 판정은 한 글자도 다르지 않았다** — 게이트는 어느 파일이 다른가만 묻고 몇 줄이 다른가는 묻지 않기 때문이다.
>
> 그래서 파일 목록은 신뢰할 수 있고 **줄 수는 환경에 따라 달라진다.** 그리고 모델은 자기 편집이 `(+2, -1)`이라고 화면에 찍힌 직후 583줄을 근거로 붙이면서 모순을 알아채지 못했다. **증거 도구의 값이 편집 규모와 어긋나면 도구를 먼저 의심하라.**

게이트 출력을 남기려면:

```
mkdir -p runs && node scripts/gate.mjs > "runs/gate-$(date +%Y-%m-%dT%H-%M).log" 2>&1; cat runs/gate-*.log | tail -20
```

`runs/`는 `.gitignore`에 있다.

## 3. 회귀 항목의 확인 해시 — 커밋 전에는 통과할 수 없다

**이 절은 v2 신규다. v1에서 매 단계마다 사람이 즉석에서 풀고 있었다.**

게이트의 `regression` 검사는 확인 해시와 **작업 트리**를 비교한다. 의존 파일이 미커밋으로 바뀐 상태에서는 어떤 해시를 적어도 차이가 남아 FAIL이다. 그런데 규약은 "커밋해도 되는 것은 exit 0뿐"이라고 한다. **두 규칙이 정면으로 부딪힌다.**

순서는 이것뿐이다.

1. 게이트가 지목한 항목을 **다시 확인한다** (자동은 러너 직접 실행, 수동은 손으로 눌러서)
2. **사람이 커밋한다** — 게이트가 아직 FAIL인 상태에서 한다
3. 확인 칸을 그 커밋 해시로 갱신한다
4. 사람이 두 번째 커밓을 한다
5. 여기서 게이트가 exit 0이 된다

**2번이 핵심 규칙의 유일한 예외다.** 그래서 조건을 좁힌다.

> **`regression` 검사만 FAIL이고, 지목된 항목을 사람이 방금 손으로 재확인했을 때만** 커밋한다. 다른 검사가 하나라도 FAIL이면 커밋하지 않는다. 재확인을 건너뛰고 커밋하면 이 절차는 형식이 되고, 그러면 회귀 원장 전체가 근거를 잃는다.

확인 칸에 날짜나 임의 문자열을 넣어 이 순서를 건너뛰려 하지 마라. 게이트가 거부한다.

> v1의 검사 7은 **날짜 기준으로 출하돼 처음부터 죽어 있었다.** 같은 날 안에서 코드가 바뀌면 날짜로는 판정할 수 없다. 하루 만에 발견됐고 커밋 해시 기준으로 바꾼 뒤에야 실제로 울렸다.

## 4. 단계가 끝났을 때

최하위 작업을 다 했다고 상위 단계가 끝난 것이 아니다. 코드베이스를 근거로 판정받는다.

1. 감사용 사본을 만든다. **실행자의 주장을 물리적으로 제거한다.**

   **v2에서 규칙이 뒤집혔다. 지울 목록이 아니라 남길 목록이다.**

   ```
   mkdir -p ../audit-tree
   # 남길 것만 복사한다
   cp SPEC.md REGRESSION.md ISSUES.md package.json .gitignore ../audit-tree/
   cp -r src ../audit-tree/          # 소스와 테스트
   cp -r scripts ../audit-tree/      # 게이트
   mkdir -p ../audit-tree/data       # 데이터 폴더는 비운 채로
   ```

   > v1은 지울 목록이었다 — `PROGRESS.md`, `RUNBOOK.md`, `CHECKS.md`, `PLAN_*.md`, `HANDOFF.md`, `*_잔여.md`. **그 목록으로는 감사가 무력화된다.** 실제로 v1 미션에서 확인한 누락은 이렇다.
   >
   > `LOG.md` — 미션 기록 전체다. 어느 단계가 결함이었고 어떻게 고쳤는지 다 적혀 있다. 키트 자신이 도입한 파일인데 목록에 없었다.
   > `AGENTS.md`(당시 `GEMINI.md`) — 이게 살아 있으면 감사 세션이 **작업 규약의 세션 시작 의례를 먼저 수행한다.** 감사 프롬프트가 그 세션을 지배하지 못한다.
   > `.git/` — 커밋 메시지가 그대로 서술이다. "ISS-002 종료", "R-007 경계 명시(오늘 포함, 7일째 포함)".
   > 데이터 파일 — 경계 시험용으로 넣어둔 값이 남아 있으면 **정답을 감사자에게 미리 알려주는 것**이다.
   >
   > 지울 것을 열거하는 방식은 파일이 하나 늘어날 때마다 구멍이 난다. 남길 것은 명세·회귀 원장·문제 원장·소스·테스트·빌드 설정뿐이다.

2. **감사 사본에서 에이전트가 뜨는지 먼저 확인한다.** 인증·환경변수가 원본 폴더에 있었다면 사본에는 없다. v1에서 첫 시도가 인증 선택창에서 멈췄다.

3. **빈 컨텍스트의 새 세션**을 열고 그 폴더에서 `PROMPTS.md` 4번을 붙인다. 이전 대화를 이어서 쓰면 무효다.

4. 판정표를 받는다. `FAIL`과 **증거 없는 `UNVERIFIABLE`**이 0건이어야 한다.

   **판정표를 받은 뒤 다음 셋을 확인한다. v1에서 감사자가 세 군데 다 샜다.**

   - **`나오면 안 되는 것` 칸이 채워졌는가.** 기준이 "A는 나오고 B는 안 나온다"인데 표에 나온 것만 적혀 있으면 절반이 증거로 안 남은 것이다.
   - **기준을 대체하지 않았는가.** 기계가 못 재는 기준을 만나면 감사자는 자기 기준을 만들어 넣고 통과를 낸다. 대체했으면 그렇게 적어야 한다.
   - **스텁 지목이 구현 코드인가.** 테스트 픽스처와 골든값은 항상 존재하므로 그걸 답으로 내면 이 장치는 결코 실패할 수 없다.

5. 0건이 아니면 남은 작업 목록을 받아 프롬프트 1로 돌아간다. 3라운드 넘게 반복하면 명세가 잘못된 것이다 — 6장 등급을 올리고 `SPEC.md`를 다시 쓴다.

6. 회귀 원장 전 항목을 한 번 확인한다(단계 종료 시에는 겹침과 무관하게 전부).

7. 조건이 다 맞으면 태그를 찍는다: `git tag green/<단계이름>`

**게이트가 그 시점에 실제로 PASS가 아니었으면 태그를 찍지 마라.** v1에서 5단계는 태그를 건너뛰고 6단계와 한 덩어리로 마감했다. `green`은 "확인된 정상 지점"이라는 뜻이고, 아닌 곳에 찍으면 되돌릴 자리가 거짓이 된다.

## 6. 작업 규모별로 절차를 줄인다

전 절차를 항상 돌리면 절차 비용이 작업 비용을 넘고, 그러면 사람이 절차를 통째로 버린다. 등급은 `PROGRESS.md`의 등급 칸에 기록한다. 승인 기록이 없는 작업은 T2로 취급한다.

| 등급 | 무엇 | 계획 | 검증 | 별도 세션 감사 |
|---|---|---|---|---|
| T0 | 문구·상수 한 줄 | 없음 | 게이트 + 내가 눌러보기 | 없음 |
| T1 | 기능 하나 | 작업 목록 3~7개 | 게이트 + 회귀 겹침 항목 | 1회 |
| T2 | 새 서브시스템 | 계획 + 단계별 작업 | 게이트 + 회귀 전체 | 1회 |
| T3 | 신규 프로젝트, 남의 코드 인수 | 계획 + 결정 로그 | 위 전부 + `CHECKS.md` | 서로 다른 프레이밍으로 2회 |

등급을 낮추지 말아야 하는 신호: 변경 파일 6개 이상, 저장 형식 변경, 외부 인터페이스 변경.

**모델에게 등급을 제안하게 할 때 이 표의 숫자를 바꿔 인용하는지 본다.** v1에서 `3~7개`를 `3~7개 미만`으로 바꿔 적었고, 그 등급이 요구하는 세 항목 중 하나만 말했다. 규정을 인용하면서 값을 바꾸는 것은 그 규정을 읽지 않았다는 신호다.

## 7. 단계는 몇 개로 쪼개는가

**요구를 먼저 센다.** 요구가 5개면 단계 5개, 12개면 묶어서 7~8개. 단계 수를 먼저 정하고 요구를 끼워넣지 않는다.

**8개를 넘기지 마라.** 넘으면 그건 앱 하나가 아니라 두 개다. 쪼개서 따로 돌린다.

**1단계는 기능이 아니라 관통이다.** 손으로 끝까지 밟을 수 있는 가장 얇은 경로 하나 — 데이터가 실제 저장 위치에 기록되고 다시 읽히는 것까지 포함한다. 재미없어 보이지만, **검증 장치가 작동한다는 것을 먼저 확인하지 않으면 나머지 단계의 PASS 전부가 근거를 잃는다.**

## 8. 하지 말 것

1. 모델이 "완벽합니다"라고 말했다는 사실을 진행 근거로 쓰지 않는다. 종료 조건은 게이트 exit 0이다.
2. 같은 세션에게 자기 작업의 완료 판정을 맡기지 않는다.
3. 예약 큐를 걸고 자리를 비운 뒤 돌아와 결과를 통과시키지 않는다. 게이트 실패의 판정은 사람이 한다.
4. 게이트가 오탐으로 울린다고 검사를 지우지 않는다. 범위를 좁히고 selftest에 정상 픽스처로 추가한다.
5. `CHECKS.md`의 빈 줄을 지워서 게이트를 통과시키지 않는다. 그건 계측기를 끄는 것이다.
6. **`gate.mjs`를 고친 뒤 selftest를 돌리지 않고 넘어가지 않는다.** v1의 검사 7이 정확히 그렇게 죽어 있었다.
7. **게이트가 PASS를 냈다는 사실을 "산출물이 맞다"로 읽지 않는다.** v1에서 게이트 PASS 상태에서 사람이 결함을 찾은 것이 네 번이다. 게이트는 뒤로 미끄러지는 것을 막는 래칫이고, 이게 맞다고 말해주는 판사가 아니다. **정확성은 사람이 판정한다.**
8. **결함을 찾을 때 "될 것 같은 자리"를 보지 않는다. "깨질 것 같은 자리"를 일부러 만든다.** v1의 네 발견 전부가 그 방법으로 나왔다 — 행의 첫날·마지막날·말일에 각각 일정을 넣어본 것, 경계 날짜를 하나씩 밟아본 것.
