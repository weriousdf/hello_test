# SPEC — 요구 목록

**이 파일은 사람만 고친다.** 모델이 고치면 대조 기준이 사라진다.
대화에서 결정된 것이 이 파일에 반영되지 않은 동안 새 작업을 시작하지 않는다.

## 3. 기능 표

**검증 기준은 기계가 잴 수 있는 문장으로 쓴다.** 이것이 v2의 핵심 규칙이다.

| 좋은 기준 | 나쁜 기준 |
|---|---|
| `모든 행이 정확히 28칸이다` | `정렬이 맞아 보인다` |
| `dday 2026-09-15 2026-12-25 가 101 을 출력한다` | `휴대폰 계산기와 대조한다` |
| `오늘+7 이 나오고 오늘+8 은 나오지 않는다` | `적당한 범위만 나온다` |

기계가 못 재는 기준은 **버리지 말고 `CHECKS.md` 로 옮긴다.** 그러면 게이트가 빈칸을 세서 사람이 확인했는지 본다.

> 왜 이 규칙이 있는가. v1 의 `R-006` 기준이 "휴대폰 D-day 계산기와 대조한다" 였다.
> 자동 감사에서 감사자에게는 휴대폰이 없다. 그래서 **자기 기준을 만들어 넣고 통과를 냈고,
> 기준을 바꿨다는 말은 하지 않았다.** 기계가 못 재는 기준은 조용히 대체된다.

R-ID 는 3자리다. `R-001` 은 인식되고 `R-01` 은 인식되지 않는다.
아래 예시 행의 `R-NNN` 은 게이트가 R-ID 로 세지 않는다. **첫 요구를 쓸 때 `R-001` 로 바꾼다.**

**상태 칸.** `계획` 은 아직 구현하지 않은 요구, `구현` 은 구현이 끝났다고 사람이 판정한 요구다.
게이트의 `unassigned_rid` 검사는 **`구현` 인 행만** 검증 수단을 요구한다. `계획` 인 행은 묻지 않는다.
이 칸은 **사람만** 옮긴다 — 단계가 끝나고 증거를 확인한 뒤에 옮긴다. 모델이 옮기면 규약 위반이다.

> 왜 이 칸이 필요한가. 이 칸이 없으면 게이트는 SPEC 의 모든 R-ID 가 검증될 때까지 FAIL 이고,
> 그러면 마지막 단계 전에는 어떤 단계도 닫을 수 없다 — 게이트가 단계 문지기 역할을 못 한다.
> v1 에서는 이 검사가 PROGRESS.md 로 충족되어 죽어 있었기 때문에 이 문제가 드러나지 않았다.
> SPEC.md 가 사람만 고치는 파일이라 모델이 이 칸을 옮겨 검사를 피할 수 없다.
