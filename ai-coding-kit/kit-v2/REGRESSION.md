# REGRESSION — 한 번 동작한 것의 원장

**모델은 항목 추가 문안을 제안만 한다.** 파일에 붙여넣는 것은 사람이 한다.
기존 항목의 기대·의존·삭제를 모델이 건드리지 않는다.

## 형식

```
- [자동|수동] <R-ID> | <무엇을 하면 무엇이 보인다> | 의존:<파일1,파일2> | 확인:<커밋해시> | mutation:<YYYY-MM-DD>
```

| 칸 | 뜻 |
|---|---|
| `[자동]` / `[수동]` | 이 항목을 무엇이 확인하는가. **v1 은 `[S]`/`[A]` 였는데 S 가 자동이고 A 가 수동이어서 외워야 알 수 있었다. v1 을 v2 로 옮기던 중 실제로 뒤집어 적는 일이 일어나 글자를 버렸다** |
| `의존:` | 이 파일들이 바뀌면 이 항목을 다시 봐야 한다. **비우면 게이트가 FAIL 을 낸다** |
| `확인:` | 마지막으로 실제 확인한 시점의 **커밋 해시**. 날짜는 인정하지 않는다 |
| `mutation:` | 이 항목이 실패를 잡는 것을 본 날. 일부러 깨뜨려 이 항목이 걸리는 것을 확인한 날짜 |

**`확인:` 이 날짜가 아니라 커밋 해시인 이유.** v1 의 회귀 검사는 날짜 기준으로 출하돼
**처음부터 죽어 있었다.** 같은 날 안에서 코드가 바뀌면 날짜로는 판정할 수 없다.
하루 만에 발견됐고 커밋 해시로 바꾼 뒤에야 실제로 울렸다.

**`mutation:` 이 있는 이유.** 실패를 잡는 것을 본 적 없는 항목은 통과에 근거를 보태지 않는다.
이 원리를 게이트 검사 자신에게 적용한 것이 `scripts/gate-selftest.mjs` 다.

**확인 해시를 갱신하는 순서** — 이 순서뿐이다. `RUNBOOK.md` 3장을 보라.

```
1. 지목된 항목 재확인   2. 커밋   3. 확인 해시 갱신   4. 두 번째 커밋   5. exit 0
```
